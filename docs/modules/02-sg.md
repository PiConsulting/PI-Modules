## 0. Decisiones tomadas antes de escribir código
 
| Decisión | Elegido | Descartado |
|---|---|---|
| Alcance | Un SG por invocación (primitivo componible) | Chain completo de 3 capas; primitivo con presets por rol |
| Egress por defecto | Abierto (`0.0.0.0/0`) | Cerrado obligatorio; cerrado solo en prod |
| Orígenes soportados en v1 | CIDR y security group | Prefix lists, IPv6, self-reference |
| Nombre del módulo | `security-group` (singular) | `security-groups` |
 
El singular no es un detalle: la convención del repositorio dice singular cuando el
módulo crea una cosa. El plural venía del roadmap original, cuando la idea era que el
módulo cableara la cadena entera.

## 1. Qué problema resuelve
 
Los security groups son el control de acceso efectivo de una arquitectura en AWS. No hay
firewall perimetral: lo que decide qué habla con qué es un conjunto de reglas repartidas
entre N grupos.
 
Y es donde más se equivoca la gente, siempre de las mismas cuatro formas:
 
**a) `0.0.0.0/0` en un puerto que no debería.** SSH abierto al mundo, Postgres accesible
desde internet, Redis sin restricción. Es el hallazgo número uno de cualquier auditoría y
la causa de una parte enorme de las brechas reales.
 
**b) Reglas sin descripción.** AWS permite `description` vacía. Un SG con 40 reglas sin
descripción es imposible de auditar: nadie sabe cuál se puede borrar, así que no se borra
ninguna y crecen para siempre.
 
**c) `DependencyViolation` al modificar un SG en uso.** Terraform intenta destruir el SG
antes de crear el nuevo, AWS lo rechaza porque hay ENIs adjuntas, y el apply muere a
medias. Se resuelve con `create_before_destroy` — que a su vez obliga a `name_prefix` en
vez de `name`, porque durante la transición conviven dos SGs y los nombres deben ser
únicos en la VPC.
 
**d) Mezclar reglas inline con recursos de regla separados.** Terraform borra en cada
apply las reglas que el otro mecanismo acaba de crear, en bucle infinito. Es un error de
diseño, no de configuración, y solo se evita eligiendo un mecanismo y no permitiendo el
otro.
 
Este módulo convierte las cuatro en imposibles.
 
### Sobre el valor real del módulo
 
Honestamente: en líneas de código, usar este módulo no ahorra mucho frente a escribir
`aws_security_group` a pelo. Lo que aporta son las validaciones que no se pueden apagar,
el `name_prefix`/`create_before_destroy` resuelto de una vez, y el etiquetado consistente.
 
**Es un módulo de disciplina, no de ahorro de tipeo.** Está bien que lo sea, pero conviene
no venderlo como otra cosa.

## 2. En qué arquitecturas se usa
 
En todas. Es, junto con la VPC, el módulo con más consumidores del catálogo.
 
| Arquitectura | SGs típicos |
|---|---|
| A. ECS Fargate + ALB | `alb`, `app`, `database`, (`cache`) |
| B. Serverless | `lambda`, `database` — solo si hay recursos en VPC |
| C. Estático + API | ninguno, salvo que el backend viva en VPC |
| D. Landing Zone | los de los servicios compartidos |
| E. Datos | `redshift`, `emr`, `glue` |
 
Depende de: `vpc` (necesita `vpc_id`).
Lo consumen: `alb`, `ecs-fargate`, `rds-aurora`, `elasticache`, `lambda`.

## 3. Buenas prácticas que debe cumplir
 
| Pilar | Requisito | Cómo se cumple |
|---|---|---|
| **Seguridad** | Nada crítico expuesto a internet | `validation` que rechaza `0.0.0.0/0` y `::/0` sobre puertos administrativos y de base de datos |
| | Toda regla justificada | `description` obligatoria y no vacía en cada entrada |
| | Sin reglas huérfanas | `validation`: cada regla necesita al menos un CIDR o un SG de origen |
| **Excelencia operativa** | Cambios sin caída | `create_before_destroy` + `name_prefix` |
| | Reglas identificables | `aws_vpc_security_group_ingress_rule` da un ID por regla y admite tags; el recurso legacy no |
| | Sin mecanismos mezclados | El módulo nunca usa bloques `ingress`/`egress` inline |
| | Trazabilidad | Mismo `local.tags` que el módulo VPC, con `Module = "security-group"` |
| **Confiabilidad** | Fallar en plan, no en apply | 5 validaciones sobre la estructura de las reglas |
| **Costes** | — | Los security groups son gratis. Único módulo del catálogo sin decisiones de coste |

## 4. Variables
 
### La decisión de interfaz que hace que el módulo funcione
 
```hcl
ingress_rules = map(object({...}))     # NO list(object({...}))
```
 
Parece cosmético. Es lo más importante del diseño.
 
Con `for_each` sobre una **lista**, la clave se deriva del contenido. Si una regla
referencia un security group creado en el mismo apply —exactamente el caso del
encadenado ALB → app → base de datos— ese ID es desconocido en tiempo de plan y Terraform
aborta con *"the given keys must be known"*. Es el fallo clásico de todos los módulos de
SG del ecosistema.
 
Con un **mapa**, la clave la elige el consumidor y siempre se conoce en plan, aunque el
valor no. La cadena completa se levanta en un solo apply sin trucos ni `depends_on`.
 
Efecto secundario valioso: la clave obliga a nombrar cada regla, y el `terraform plan`
muestra `["postgres-desde-app"]` en lugar de `[3]`.
 
### Interfaz completa
 
| Variable | Tipo | Default | Notas |
|---|---|---|---|
| `name` | `string` | — | `<cliente>-<entorno>-<rol>`, ej. `acme-prod-alb`. Se usa como `name_prefix` |
| `environment` | `string` | — | `dev` \| `stg` \| `prod` |
| `vpc_id` | `string` | — | Del output `vpc_id` del módulo vpc |
| `description` | `string` | — | Del SG. Sin default: AWS pone "Managed by Terraform", que no dice nada |
| `ingress_rules` | `map(object)` | `{}` | Ver estructura abajo |
| `egress_rules` | `map(object)` | `{}` | Misma estructura. Solo se aplica si `allow_all_egress = false` |
| `allow_all_egress` | `bool` | `true` | Comportamiento por defecto de AWS. Evita ciclos y el 80% de los tickets de conectividad |
| `tags` | `map(string)` | `{}` | |
 
Estructura de una regla:
 
```hcl
{
  description               = string                        # obligatoria
  from_port                 = number
  to_port                   = number
  protocol                  = optional(string, "tcp")
  cidr_blocks               = optional(list(string), [])
  source_security_group_ids = optional(list(string), [])
}
```
 
### Validaciones
 
| Regla | Qué previene |
|---|---|
| `description` no vacía en toda entrada | SGs inauditables |
| Sin `0.0.0.0/0` ni `::/0` sobre 22, 3389, 5432, 3306, 1433, 6379, 27017, 9200, 11211 | El hallazgo de seguridad más común que existe |
| `from_port <= to_port` | Fallo en apply a mitad de despliegue |
| Al menos un `cidr_blocks` o un `source_security_group_ids` por regla | Reglas que no hacen nada y nadie detecta |
| `protocol` en `tcp`, `udp`, `icmp`, `icmpv6`, `-1` | Erratas silenciosas |
 
La validación de puertos administrativos no puede referenciar un `local`, así que la
lista de puertos va inline en el bloque `validation`. Es feo y es la única forma:
 
```hcl
validation {
  condition = alltrue([
    for key, rule in var.ingress_rules : !(
      anytrue([for c in rule.cidr_blocks : c == "0.0.0.0/0" || c == "::/0"]) &&
      anytrue([
        for p in [22, 3389, 5432, 3306, 1433, 6379, 27017, 9200, 11211] :
        rule.from_port <= p && rule.to_port >= p
      ])
    )
  ])
  error_message = "Prohibido exponer puertos administrativos o de base de datos a 0.0.0.0/0 o ::/0."
}
```
 
Nótese que comprueba **rangos**, no puertos exactos: una regla `0-65535` desde
`0.0.0.0/0` también se rechaza, que es justo el caso que la gente escribe "temporalmente".

## 5. Outputs
 
| Output | Consumido por |
|---|---|
| `id` | Todo: `alb`, `ecs-fargate`, `rds-aurora`, y otras invocaciones de este mismo módulo para encadenar |
| `arn` | Políticas IAM que restringen por SG |
| `name` | Nombre real generado a partir del `name_prefix` |
| `ingress_rule_ids` | Mapa clave → ID de regla. Para auditoría y para políticas que referencian una regla concreta |
| `egress_rule_ids` | Ídem |
 
`id` es el output que sostiene el encadenado, y por eso el módulo no expone nada más
complejo: cuanto más simple sea la superficie, más fácil es componer.

## 6. Recursos que crea
 
| Recurso | Cantidad |
|---|---|
| `aws_security_group` | 1 |
| `aws_vpc_security_group_ingress_rule` | 1 por cada (CIDR o SG origen) de cada entrada del mapa |
| `aws_vpc_security_group_egress_rule` | 1 si `allow_all_egress`, si no 1 por destino |
 
### El aplanado
 
Una entrada del mapa con 2 CIDRs y 1 SG de origen produce 3 recursos de regla. Se
normalizan ambos orígenes a la misma forma de objeto —con `null` en el campo que no
aplica— para poder usar **un solo** recurso con un `for_each`, en lugar de dos recursos
distintos:
 
```hcl
locals {
  ingress_from_cidr = merge([
    for key, rule in var.ingress_rules : {
      for idx, cidr in rule.cidr_blocks :
      "${key}-cidr-${idx}" => {
        description                  = rule.description
        from_port                    = rule.from_port
        to_port                      = rule.to_port
        protocol                     = rule.protocol
        cidr_ipv4                    = cidr
        referenced_security_group_id = null
      }
    }
  ]...)
 
  ingress_from_sg = merge([
    for key, rule in var.ingress_rules : {
      for idx, sg in rule.source_security_group_ids :
      "${key}-sg-${idx}" => {
        description                  = rule.description
        from_port                    = rule.from_port
        to_port                      = rule.to_port
        protocol                     = rule.protocol
        cidr_ipv4                    = null
        referenced_security_group_id = sg
      }
    }
  ]...)
 
  ingress_rules_flat = merge(local.ingress_from_cidr, local.ingress_from_sg)
}
```
 
**Limitación conocida y aceptada:** el índice de la clave sale de la posición en la lista.
Reordenar `cidr_blocks` recrea esas reglas. Es barato —una regla de SG se recrea en
segundos y no hay pérdida de datos— y la alternativa (claves derivadas del valor) rompe
el caso de los IDs desconocidos, que es precisamente lo que este diseño resuelve. Va
documentado en el README.
 
### `name_prefix`, no `name`
 
`create_before_destroy = true` es obligatorio: sin él, modificar un SG con ENIs adjuntas
falla con `DependencyViolation`.
 
Pero `create_before_destroy` obliga a `name_prefix`: durante la transición conviven el SG
viejo y el nuevo, y los nombres deben ser únicos dentro de la VPC. Con `name` fijo, el
apply falla con `InvalidGroupName.Duplicate`.
 
Es un detalle no obvio que produce fallos intermitentes —solo aparece al *modificar*, no
al crear— y resolverlo una sola vez en el módulo es literalmente la mitad de su razón de
ser.

## 7. Decisiones que el módulo NO debe tomar
 
| Decisión | De quién es |
|---|---|
| Qué SGs existen y cómo se encadenan | Root, o `patterns/web-app-ecs` cuando exista |
| Qué puertos usa la aplicación | Root: es una propiedad del workload, no de la red |
| Si el egress debe cerrarse | Root, vía `allow_all_egress = false` |
| A qué recursos se adjunta el SG | Los módulos de cómputo y datos |
| El SG por defecto de la VPC | Ya lo gestiona y vacía el módulo `vpc` |
| Reglas entre cuentas o vía peering | Fuera de alcance hasta que exista el caso |

## 8. Errores comunes que evita
 
| Error | Consecuencia | Cómo lo evita |
|---|---|---|
| `0.0.0.0/0` en 22 o 5432 | Brecha | `validation`, sin variable para desactivarla |
| Rango `0-65535` abierto "temporalmente" | Ídem | La validación comprueba rangos, no puertos exactos |
| Reglas sin descripción | SG inauditable que crece para siempre | `validation` de longitud mínima |
| `DependencyViolation` al modificar | Apply a medias en producción | `create_before_destroy` |
| `InvalidGroupName.Duplicate` | El fix anterior mal hecho | `name_prefix` |
| Mezclar inline y recursos separados | Reglas que se borran solas en cada apply | El módulo nunca usa inline |
| `for_each` sobre lista con IDs desconocidos | No se puede levantar la cadena en un apply | Mapa con clave del consumidor |
| Regla sin origen | No hace nada, nadie lo nota | `validation` |

## 10. Uso desde el repositorio live
 
```hcl
# 20-security/main.tf
 
module "sg_alb" {
  source = "git::https://github.com/benjamin-cloud-pi/PI-Modules.git//modules/security-group?ref=security-group/v1.0.0"
 
  name        = "${var.name_prefix}-alb"
  environment = var.environment
  vpc_id      = data.aws_vpc.this.id
  description = "ALB publico de la plataforma"
 
  ingress_rules = {
    "https-internet" = {
      description = "HTTPS desde internet"
      from_port   = 443
      to_port     = 443
      cidr_blocks = ["0.0.0.0/0"]
    }
    "http-redirect" = {
      description = "HTTP, solo para redirigir a HTTPS"
      from_port   = 80
      to_port     = 80
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
 
  tags = local.common_tags
}
 
module "sg_app" {
  source = "...//modules/security-group?ref=security-group/v1.0.0"
 
  name        = "${var.name_prefix}-app"
  environment = var.environment
  vpc_id      = data.aws_vpc.this.id
  description = "Tareas ECS de la aplicacion"
 
  ingress_rules = {
    "app-desde-alb" = {
      description               = "Trafico de aplicacion desde el ALB"
      from_port                 = 8080
      to_port                   = 8080
      source_security_group_ids = [module.sg_alb.id]
    }
  }
 
  tags = local.common_tags
}
 
module "sg_database" {
  source = "...//modules/security-group?ref=security-group/v1.0.0"
 
  name        = "${var.name_prefix}-database"
  environment = var.environment
  vpc_id      = data.aws_vpc.this.id
  description = "Aurora PostgreSQL"
 
  ingress_rules = {
    "postgres-desde-app" = {
      description               = "Postgres desde las tareas ECS"
      from_port                 = 5432
      to_port                   = 5432
      source_security_group_ids = [module.sg_app.id]
    }
  }
 
  tags = local.common_tags
}
```
 
Las tres invocaciones se resuelven en un solo `apply`. El grafo es lineal —alb, luego
app, luego database— y no hay ciclo porque la cadena se expresa **solo con reglas de
ingress**. Es la razón de fondo por la que el egress va abierto por defecto.

## 11. Versionado
 
**Tag:** `security-group/vMAJOR.MINOR.PATCH`
 
| Cambio | Bump |
|---|---|
| Cambiar la forma del objeto de regla | **MAJOR** |
| Pasar `allow_all_egress` a `false` por defecto | **MAJOR** |
| Cambiar el esquema de claves del aplanado (recrea todas las reglas) | **MAJOR** |
| Añadir puertos a la lista de prohibidos | **MAJOR** — puede romper a un consumidor existente |
| Soporte de prefix lists tras campo opcional | MINOR |
| Soporte IPv6 tras campo opcional | MINOR |
| Nuevo output | MINOR |
| Mensaje de error más claro | PATCH |
 
La cuarta fila es contraintuitiva y conviene tenerla presente: endurecer una validación
es un cambio incompatible, porque un consumidor que hoy pasa el plan mañana no lo pasa.

## 12. Checklist antes de producción
 
**Seguridad**
 
- [ ] Ningún SG con `0.0.0.0/0` fuera de 80 y 443 en el SG del ALB
- [ ] La capa de aplicación solo acepta tráfico desde el SG del ALB, nunca por CIDR
- [ ] La capa de datos solo acepta tráfico desde el SG de aplicación
- [ ] Toda regla tiene una descripción que explica el *por qué*, no el *qué*
- [ ] Ningún SG tiene reglas que nadie sabe justificar
**Operación**
 
- [ ] Los nombres siguen `<cliente>-<entorno>-<rol>`
- [ ] Se ha probado **modificar** un SG ya adjunto a un recurso, no solo crearlo — es el
      escenario donde aparece `DependencyViolation`
- [ ] Tags completos
- [ ] `terraform destroy` limpio
**Diseño**
 
- [ ] Si `allow_all_egress = false`, están cubiertos DNS, NTP, los VPC endpoints y las
      actualizaciones de paquetes
- [ ] Las claves del mapa describen la regla y son estables
